# CS2 Data Attributes

Ниже — короткий список ключевых атрибутов структурированного соревновательного домена CS2, которые стоит явно хранить в системе как часть доменной модели. Этот документ является canonical-описанием именно storage-модели для структурированных соревновательных CS2-сущностей: матчей, карт, veto, турниров, команд, игроков, составов и рейтингов. Identity resolution, external IDs и source mapping фиксируются отдельно. Чтобы не смешивать первичные данные и производные значения, для каждого атрибута отдельно отмечено, является ли он исходным (`raw`) или агрегированным / расчётным (`derived`).

Этот документ описывает только предметные атрибуты структурированных соревновательных CS2-сущностей. Служебные данные загрузки, такие как источник, время получения, статус полноты, правила сопоставления и разрешение конфликтов, описываются отдельно.

Документ не покрывает новостные сущности и другие неструктурированные части acquisition scope из PRD. PRD фиксирует acquisition categories первого этапа, а этот документ фиксирует, как структурированные категории проецируются в storage-модель. В частности, категория `schedule` из PRD здесь выражается через match-level атрибуты времени и статуса, без отдельной первичной schedule-сущности; модель хранит актуальное состояние расписания без истории его изменений. Категория `transfers` из PRD здесь выражается через историчность membership-записей состава; отдельная первичная transfer-сущность пока не требуется, поскольку переходы между командами восстанавливаются из membership-периодов.

## Priority Categories

### Матч

| MCH-01 | Запланированное время матча | `raw` | `datetime_or_null` | `2026-03-21T18:30:00Z` | Нужно для расписания, upcoming-сценариев и временных срезов |
| MCH-02 | Формат матча (`Bo1/Bo3/Bo5`) | `raw` | `enum` | `Bo3` | Нужен для интерпретации сценария серии |
| MCH-03 | Статус матча | `raw` | `enum` | `finished` | Нужен для различения upcoming/live/finished |
| MCH-04 | Участники матча | `raw` | `team_ref[]` | `[team-spirit, natus-vincere]` | Нужны для связи матча с командами |
| MCH-05 | Турнир матча | `raw` | `tournament_ref` | `iem-katowice-2026` | Нужен для связи матча с турнирным контекстом |
| MCH-06 | Стадия турнира для матча | `raw` | `enum` | `playoffs` | Нужна как контекст конкретного матча, а не всего турнира целиком |

| MCH-10 | Итоговый счёт матча, пересчитанный системой | `derived` | `series_score` | `2:1` | Нужен для валидации и унификации, когда результаты карт полны и согласованы |

| ID | Атрибут | Тип | Тип данных | Пример | Зачем нужен |
| --- | --- | --- | --- | --- | --- |
| MEM-01 | Команда | `raw` | `team_ref` | `team-spirit` | Нужна для исторической связи игрока с командой |
| MEM-02 | Игрок | `raw` | `player_ref` | `donk` | Нужен для исторической связи игрока с командой |
| MEM-03 | Дата вступления в команду | `raw` | `date` | `2024-07-01` | Нужна для оценки сыгранности и восстановления состава на дату матча |
| MEM-04 | Дата ухода из команды | `raw` | `date_or_null` | `2026-02-12` | Нужна для завершения периода membership и восстановления трансферов |
| MEM-05 | Роль в составе | `raw` | `enum` | `starter` | Нужна, чтобы различать active roster, bench, stand-in, coach и похожие типы связи |
| MEM-06 | Статус membership | `raw` | `enum` | `active` | Нужен для различения active, benched, loan, trial и других состояний участия |
| MEM-07 | Период действия membership | `derived` | `daterange` | `[2024-07-01, 2026-02-12)` | Удобен для запросов по историческому составу |

Для membership `role` означает спортивную или функциональную роль в ростере, а `status` означает состояние участия или контрактного отношения.

### Игрок

| ID | Атрибут | Тип | Тип данных | Пример | Зачем нужен |
| --- | --- | --- | --- | --- | --- |
| PLY-01 | Ник игрока | `raw` | `string` | `donk` | Нужен как основное имя / display-атрибут сущности игрока |
| PLY-02 | Основная роль игрока (`primary_role`) | `raw` | `string_or_null` | `rifler` | Нужна как source-reported label для базового player-level контекста раннего этапа |
| PLY-03 | Дата рождения игрока | `raw` | `date` | `2007-01-25` | Нужна как canonical-источник для расчёта возраста и демографического контекста |
| PLY-04 | Национальность игрока | `raw` | `country_code` | `RU` | Нужна для контекста языка и региона |

Если у игрока потенциально несколько ролей, в этой модели сохраняется его основная роль как наиболее стабильный и полезный для раннего этапа атрибут.

Для player age canonical-значением остаётся `birth_date`; абстрактный "текущий возраст" не должен трактоваться как самостоятельный persisted-атрибут. Возраст является derived query metric и должен вычисляться от `birth_date` и внешней reference date, например даты матча или даты snapshot.

Для карты `team_ref_to_side_map` задаёт стартовые стороны как явное отображение `team_ref -> side`, а round history должна хранить победителя как `team_ref` и отдельно фиксировать сторону и фазу (`period`) раунда. Это нужно, чтобы данные оставались аналитически корректными после смены сторон и в overtime.

Для veto `initiator_team_ref_or_null` не должен смешивать "неприменимо" и "неизвестно". Значение `null` валидно только для системных действий, где инициатор по смыслу отсутствует; если у действия должен быть инициатор, но источник его не дал, это должно трактоваться как missing / incomplete data, а не как корректное пустое значение.

Для региона используется единый справочник `region_code`, но смысл поля должен быть явным в имени атрибута: `event_region` для турниров и `competitive_region` для команд. Значения из разных справочников или разных уровней абстракции под одним и тем же полем недопустимы.

`derived` здесь не означает, что поле запрещено хранить. Это пометка, что источник истины находится на более детальном уровне, а само значение логически является производным и может быть пересчитано при необходимости. Для source-reported (`raw`) и derived score ожидается, что система умеет хранить оба варианта, если источник присылает готовый счёт, а детальность map/round-данных недостаточна или конфликтует с ним.

## Out Of Scope For Now

- Информация о том, посредством каких источников будут загружаться указанные данные
- Позиции игроков на картах
- Новости и неструктурированные новостные сущности
- Тонкий разбор utility usage и micro-patterns
- Неустойчивые qualitative-сигналы из соцсетей без явного источника и структуры
- Производные метрики вроде формы команды, map pool, винрейтов и частоты пиков/банов
- Intra-round event-level телеметрия, если для текущих сценариев достаточно хранить победителя раунда и способ победы
- Букмекерские линии и движение коэффициентов
