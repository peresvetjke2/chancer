# PRD-002: PandaScore Data Acquisition

## Problem

Продукту нужен предсказуемый и повторяемый способ получать структурированные CS2-данные из PandaScore. Сейчас в проекте уже есть следы интеграции с этим источником, но на уровне product requirements не зафиксировано, какую именно capability должна дать PandaScore-интеграция, какие сущности считаются обязательными, какие ограничения качества и свежести важны и где проходит граница инициативы.

Без такого PRD downstream-реализация рискует превратиться в набор точечных импортов без общего контракта: неясно, какие данные считаются минимально достаточными, какие сценарии обновления обязательны, как трактовать частичные ответы API и какие пробелы PandaScore допустимы, а какие считаются блокером для продукта.

Инициатива нужна, чтобы оформить PandaScore как явный acquisition capability, а не как набор ad hoc запросов к внешнему API.

## Users And Jobs

| User / Segment | Job To Be Done | Current Pain |
| --- | --- | --- |
| `system-operator` | Запускать и повторять загрузку данных из PandaScore без ручной доработки по каждой сущности | Не определены обязательные сценарии синхронизации и критерии успешной загрузки |
| `product-owner` | Понимать, какие данные PandaScore реально поставляет и на что можно опираться в продукте | Нет явной рамки coverage, freshness и ограничений источника |
| `downstream-feature-owner` | Использовать в приложении согласованные данные по матчам, командам и игрокам | Нет зафиксированного продуктового контракта на полноту и качество импортируемых данных |

## Goals

- `G-01` Зафиксировать PandaScore как поддерживаемый источник структурированных CS2-данных для продукта.
- `G-02` Определить минимально обязательный набор сущностей и атрибутов, которые инициатива должна поставлять в локальную систему.
- `G-03` Зафиксировать ожидания к свежести, повторяемости и качеству загрузки данных из PandaScore.
- `G-04` Снизить риск того, что downstream-фичи будут зависеть от неформализованных или случайно доступных полей API.

## Non-Goals

- `NG-01` Этот PRD не описывает UI, аналитику, прогнозные модели или пользовательское представление данных.
- `NG-02` Этот PRD не фиксирует конкретную реализацию клиентских классов, rake tasks, очередей или схемы хранения.
- `NG-03` Этот PRD не обещает покрытие всех возможных сущностей PandaScore за пределами согласованного baseline scope.
- `NG-04` Этот PRD не определяет multi-source стратегию; речь идет именно о capability сбора данных из PandaScore.

## Product Scope

Инициатива описывает продуктовый контракт на ingestion данных из PandaScore для CS2-домена.

### In Scope

- Получение и обновление данных по матчам, командам и игрокам из PandaScore.
- Поддержка baseline-сценариев первичной загрузки и повторной синхронизации.
- Явная фиксация обязательных атрибутов и допустимых partial-results по каждой baseline-сущности.
- Фиксация требований к идентификации записей PandaScore внутри локальной модели данных.
- Обозначение продуктовых правил на случай пропусков, устаревших данных и неполных ответов API.

### Out Of Scope

- Сбор данных из HLTV, Liquipedia и других внешних источников.
- Обогащение данных вручную или через отдельный editorial workflow.
- Реализация продвинутой оркестрации, фонового планирования и мониторинга вне минимально нужного ingestion contract.
- Все сущности PandaScore, которые не нужны для baseline use cases текущего продукта.

## UX / Business Rules

- `BR-01` PandaScore используется как продуктово одобренный внешний источник только для явно перечисленного baseline-набора сущностей и атрибутов.
- `BR-02` Для `match`, `team` и `player` должен быть определен mandatory attribute set, без которого запись не считается пригодной для downstream-использования.
- `BR-03` Система должна различать как минимум состояния `complete`, `partial` и `failed` для результата загрузки сущности или батча.
- `BR-04` Частичная загрузка допустима только если downstream-потребители могут явно отличить incomplete-данные от полных.
- `BR-05` Каждая импортированная baseline-сущность должна сохранять устойчивую связь с идентификатором PandaScore.
- `BR-06` Если PandaScore не покрывает нужный атрибут или возвращает его нестабильно, это должно быть явно отмечено как gap, а не замаскировано пустым значением без контекста.
- `BR-07` Повторный запуск синхронизации не должен требовать ручного восстановления уже известных PandaScore identity links.
- `BR-08` Инициатива считается полезной только если покрывает как историческую загрузку baseline-данных, так и регулярное обновление новых или изменившихся записей.

## Success Metrics

| Metric ID | Metric | Baseline | Target | Measurement method |
| --- | --- | --- | --- | --- |
| `MET-01` | Доля baseline ingestion runs, завершающихся без ручного вмешательства | Не определено | >= 90% | Логи и отчеты по запускам загрузки |
| `MET-02` | Доля baseline-сущностей с сохраненным PandaScore identity link | Частично или не формализовано | 100% для `match`, `team`, `player` в agreed scope | Проверка данных и verify-отчеты |
| `MET-03` | Доля mandatory attributes, формально покрытых продуктовым контрактом | 0% | 100% для baseline scope | Ревью PRD и downstream verify contracts |
| `MET-04` | Доля записей, классифицированных как `complete` или допустимо `partial` | Не определено | >= 95% | Data quality reports по результатам синхронизации |
| `MET-05` | Соблюдение согласованной свежести данных для активных матчей и связанных сущностей | Не определено | 100% для утвержденных сценариев обновления | Сравнение timestamps синхронизации с agreed thresholds |

## Risks And Open Questions

- `RISK-01` Реальное покрытие PandaScore по CS2 может оказаться уже, чем ожидается продуктом.
- `RISK-02` Некоторые поля PandaScore могут быть неполными, запаздывающими или нестабильными между повторными запросами.
- `RISK-03` Если baseline scope не зафиксировать рано, реализация уйдет в избыточный импорт второстепенных сущностей вместо критичного минимума.
- `RISK-04` Downstream-фичи могут начать зависеть от полей, которые доступны в API сегодня, но не оформлены как обязательный контракт инициативы.
- `OQ-01` Какие сущности кроме `match`, `team` и `player` должны входить в baseline первого этапа: `tournament`, `serie`, `opponent`, `roster`, `league`?
- `OQ-02` Нужна ли первой версии инициативы поддержка backfill по историческим матчам, или достаточно forward-sync для новых и обновляемых событий?
- `OQ-03` Какие thresholds freshness действительно нужны для завершенных матчей, будущих матчей и карточек команд?
- `OQ-04` Какие gaps PandaScore приемлемы для продукта без обязательного fallback на другой источник?
