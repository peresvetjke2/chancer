# PRD-001: Internet Data Acquisition

## Problem

Чтобы строить надёжную аналитику и прогнозы по матчам CS2, продукту нужен устойчивый слой сбора данных из интернета. Сейчас project-wide контекст фиксирует важность истории матчей, составов, рейтингов, статистики игроков и новостей, но не определяет продуктовый scope отдельной инициативы по acquisition layer.

Проблема первого этапа в том, что данные нужны из нескольких внешних источников с разной природой доступа: официальные и полуофициальные API, HTML-страницы со скраппингом, источники новостей и справочные площадки. Без единого capability-слоя система не может последовательно отвечать на вопросы:

- какие источники считаются допустимыми и приоритетными;
- какие сущности обязаны покрываться уже на первом этапе;
- как отличать пригодные данные от частичных, устаревших или конфликтующих;
- как организовать сбор как greenfield-инициативу, не считая текущую реализацию ограничением.

Этот PRD сознательно рассматривает тему интернет-сбора данных как отдельную инициативу и не наследует текущие importers, rake tasks или существующие интеграции как продуктовую рамку. Для целей этой инициативы допустимо спроектировать и реализовать capability заново, если это упрощает дальнейшее развитие.

## Users And Jobs

| User / Segment | Job To Be Done | Current Pain |
| --- | --- | --- |
| `better-user` | Получить прогноз и аналитику, основанные на свежих и полных данных | Данные в продукте могут быть неполными, устаревшими или покрывать только часть signal space |
| `product-owner` | Понять, какие интернет-источники покрывают ключевые сущности и насколько им можно доверять | Нет единой рамки приоритетов источников, качества и coverage |
| `system-operator` | Запускать и контролировать обновление данных без ручного разруливания по каждому источнику | Сбор из разных типов источников не оформлен как единая capability с понятными правилами |

## Goals

- `G-01` На первом этапе продукт получает единый capability-layer для сбора данных из интернета по ключевым CS2-сущностям: команды, матчи, составы, рейтинги, игроки, новости.
- `G-02` Инициатива поддерживает несколько типов источников: API и scraping, без продуктового перекоса только в одну модель доступа.
- `G-03` Для каждой категории данных определены source priority, минимальные требования к freshness и правила разрешения конфликтов между источниками.
- `G-04` Scope первого этапа допускает greenfield-реализацию и не требует совместимости с текущими importers как самоцели.
- `G-05` Downstream features аналитики и прогнозирования получают предсказуемую и расширяемую базу данных, а не набор точечных одноразовых загрузчиков.

## Non-Goals

- `NG-01` Этот PRD не описывает саму аналитику, прогнозную модель, чат-интерфейс или UX для конечного пользователя.
- `NG-02` Этот PRD не фиксирует конкретную архитектуру классов, очередей, таблиц или схемы orchestration.
- `NG-03` Инициатива первого этапа не обязана сохранять текущий код сбора данных, если он мешает целостному redesign подхода.
- `NG-04` На первом этапе не требуется покрыть все возможные внешние источники; нужен управляемый и расширяемый baseline.
- `NG-05` Ручной research источников без последующей продуктовой формализации не считается завершением инициативы.

## Product Scope

Инициатива покрывает capability-level слой, который умеет получать интернет-данные из разных источников, приводить их к каноничным сущностям проекта и делать этот слой пригодным для дальнейшей аналитики.

### In Scope

- Определение набора поддерживаемых source types: API, HTML scraping, news feeds или эквивалентные интернет-каналы.
- Определение канонических категорий данных первого этапа: команды, матчи, расписание, составы, рейтинги, игроки, новости и трансферы.
- Фиксация source priority по каждой категории данных.
- Фиксация правил freshness, completeness и conflict resolution на уровне capability.
- Возможность повторяемого запуска сбора данных по источнику и по категории сущностей.
- Подготовка downstream-слоя для feature packages аналитики, прогноза и пользовательских ответов.

### Out Of Scope

- Формирование betting recommendations и probabilistic model output.
- Пользовательский чат, UI-ленты и объяснение прогнозов.
- Авторизация, персонализация и пользовательская история.
- Полная автоматизация всех cron/scheduling сценариев, если она не нужна для завершения первого этапа capability.
- Обязательная совместимость с текущими точечными интеграциями, импортёрами и историческими решениями.

## UX / Business Rules

- `BR-01` Любая категория данных первого этапа должна иметь явно определённый primary source и хотя бы одну допустимую стратегию fallback, если primary source недоступен или недостаточен.
- `BR-02` Продукт не должен считать существующую реализацию сбора данных канонической рамкой для этой инициативы; greenfield-подход разрешён по умолчанию.
- `BR-03` Сбор из интернета должен уважать внешние ограничения источников: rate limits, robots/rules доступа, anti-bot ограничения и лицензионные оговорки.
- `BR-04` Для каждой записи должно быть возможно определить provenance: из какого источника и каким способом она получена.
- `BR-05` Конфликтующие данные из разных источников не должны молча смешиваться без зафиксированного приоритета или явного правила разрешения.
- `BR-06` Частично успешный сбор допустим, если система умеет явно отделять complete, partial и failed result по источнику или категории.
- `BR-07` Первый этап должен завершиться не только research-результатом, но и работающей реализацией capability хотя бы для минимально достаточного набора категорий данных.

## Success Metrics

| Metric ID | Metric | Baseline | Target | Measurement method |
| --- | --- | --- | --- | --- |
| `MET-01` | Доля ключевых категорий данных первого этапа, для которых есть рабочий интернет-источник | 0% как formalized capability | 100% для согласованного baseline-набора категорий | Сверка PRD scope с реализованными downstream features |
| `MET-02` | Доля категорий данных, где зафиксирован source priority и fallback policy | 0% | 100% | Ревью capability-спецификаций и feature packages |
| `MET-03` | Доля записей, для которых сохраняется provenance источника | Не определено | 100% для данных, собранных в рамках новой capability | Проверка downstream verify-контрактов |
| `MET-04` | Доля запусков сбора, завершающихся без ручного вмешательства оператора | Не определено | >= 90% на baseline-сценариях | Логи verify/manual runs по feature packages |

## Risks And Open Questions

- `RISK-01` Часть ценных источников может оказаться нестабильной из-за anti-bot защиты, rate limits или юридических ограничений.
- `RISK-02` Разные источники могут давать несовместимые идентификаторы, таймзоны, naming conventions и степень детализации.
- `RISK-03` Попытка покрыть слишком много категорий и источников сразу может размыть первый этап и затормозить доставку.
- `RISK-04` Greenfield-подход может потребовать частичного выбрасывания уже работающего кода, что увеличит краткосрочную стоимость изменений.
- `OQ-01` Какой baseline-набор источников и категорий данных достаточно считать обязательным для завершения первого этапа?
- `OQ-02` Какие источники допустимы юридически и операционно для production-like использования, а какие годятся только для research/prototype?
- `OQ-03` Нужна ли на первом этапе единая стратегия identity resolution для команд, игроков и турниров между несколькими источниками?
- `OQ-04` Какой уровень near-real-time freshness действительно нужен для разных категорий данных: матчи, ростеры, новости, рейтинги?
