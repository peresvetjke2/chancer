# 01 Review

## Task

Проведи критическое ревью ADR как canonical decision record.

## Input

- путь к файлу ADR.

## Allowed Sources

Используй только:

- сам ADR;
- `memory-bank/flows/templates/adr/ADR-XXX.md`;
- `memory-bank/dna/frontmatter.md`;
- `memory-bank/adr/README.md`;
- документы из `derived_from`, если они существуют;
- явно связанные документы, если они существуют.

## Focus

- найти содержательные замечания;
- выявить нарушения ADR-контракта проекта;
- отделить исправимые проблемы от вопросов, где нужен человек.

Проверяй ADR по таким критериям:

- соблюдена ли базовая структура: `Контекст`, `Драйверы решения`, `Рассмотренные варианты`, `Решение`, `Последствия`, `Риски и mitigation`, `Follow-up`, `Связанные ссылки`;
- согласованы ли формулировки с `decision_status`:
  - для `proposed` нельзя писать так, будто решение уже окончательно принято;
  - для `accepted` решение должно быть зафиксировано как уже принятое;
- достаточно ли контекста и драйверов, чтобы понять, почему вообще возник выбор;
- есть ли реальные альтернативы и понятный trade-off, а не только один вариант;
- объясняет ли секция `Решение`, что именно выбирается, где действуют границы решения и что исключено из scope;
- описаны ли последствия, риски и follow-up достаточно конкретно для downstream-работы;
- есть ли ссылки на связанные документы, если ADR опирается на них;
- нет ли implementation leakage, который должен жить не в ADR, а в implementation-плане или другом downstream-документе;
- нет ли явных противоречий, пустых секций, тавтологии, расплывчатых формулировок и неподтвержденных скачков логики.

Не придумывай факты, которых нет во входе. Если информации не хватает, подними вопрос вместо домысливания.

Считай `issue` замечанием, если его можно обосновать по тексту ADR и оно снижает качество решения как документа.
Считай `question` вопросом, если без ответа человека нельзя надежно устранить неоднозначность.

Правила приоритизации:

- не размывай результат мелкими stylistic-замечаниями;
- если есть проблемы, делающие ADR непригодным как decision record, ставь их выше локальных недочетов структуры;
- если нарушен ADR-контракт проекта, явно называй проблемное поле, секцию или источник;
- если не хватает evidence или исходного контекста, не маскируй это под обычный editorial comment.

## Output

Верни только JSON с полями:
- `issues`
- `questions`

Используй такой контракт:

```json
{
  "issues": [
    {
      "id": "ISSUE-01",
      "severity": "high | medium | low",
      "section": "Название секции ADR или frontmatter",
      "summary": "Короткая формулировка проблемы",
      "why_it_matters": "Почему это ухудшает ADR",
      "recommended_fix": "Какой правки ожидает ревью"
    }
  ],
  "questions": [
    {
      "id": "QUESTION-01",
      "section": "Название секции ADR или frontmatter",
      "question": "Что нужно уточнить у человека",
      "why_answer_is_needed": "Почему без этого нельзя уверенно улучшить ADR"
    }
  ]
}
```

Правила вывода:

- если замечаний или вопросов нет, верни пустой массив;
- не добавляй текст вне JSON;
- не переписывай ADR в этом шаге;
- не смешивай issue и question в одном объекте.
